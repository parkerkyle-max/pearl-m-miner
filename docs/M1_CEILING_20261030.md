# M1 Max：算力上限、矩阵分块优化与验证边界

2026-10-30；Apple M1 Max，实读 32 核 GPU、64 GiB，macOS 26.6.1，接电。

**本轮找到并采用 32×64 分块优化。** 两次 60 秒完整新网格候选扫描均值为
4.2344 PRL TH/s，较四次旧版控制均值 3.9272 提升约 **7.82%**；随后 300 秒持续扫描为
**4.2347 TH/s**。这是相对本机此前 Alpha 2 的 S-prefix 后端，不是重新与
Pearly 或上游矿工对照，也不是矿池有效算力、收入或其他 M 芯片的增益。

精确的发布副本通过独立数值、transcript/hash/target、官方 proof 检查后，才替换本机
shader；部署路径又通过官方自测和 45 秒 CLI 基准。矿池身份、1% active-scan 开发费、
任务过期处理及温度保护没有改变。部署后的独立 Kryptex 用户会话已记录 1 份接受回复，每条都关联本地 proof 校验、gzip 提交 ID、任务 ID 与新 shader 指纹；开发费会话不计入。这是兼容性证据，不是精确的矿池算力／收益估计。见 [live 收据](data/m1-pair32-live.json)。

## 能否给出理论上限？

对**当前直接矩阵计算路径**，可以给出有前提的算术上限估算，不能证明所有合法
Pearl 算法或整个 SoC 的绝对上限。

一个当前 tile 的协议工作量是 `2×64×(4096/128)×128 = 524288`。
扫描也需要 `32×2×64×128 = 524288 MAC`，一 MAC 计乘法＋加法两次操作，
即 `1048576 FLOP/tile`。所以当前实现的 **1 PRL TH/s 对应约 2 TFLOP/s 主扫描工作**。

[Apple 对基础 8 核 M1 给出 2.6 TFLOPS](https://www.apple.com/ca/newsroom/2020/11/apple-unleashes-m1/)。
按同速核心扩展到 32 核得到约 `2.6×32/8 = 10.4 TFLOPS`。本轮没有找到 Apple
直接把 10.4 标给 M1 Max 混合精度路径的原始规格，因此这里明确称为缩放估算。

若 10.4 TFLOPS 适用于该路径：

```
只计扫描：             10.4 / 2 = 5.20 PRL TH/s
再计当前 S→X 矩阵准备： 5.20 / (1 + 1024/524288) ≈ 5.19 PRL TH/s
```

X 的 1024 MAC/tile 摊销取当前 `M=16384、N=65536` 且完整扫描新网格；任务过期或
只扫描部分网格时，每份有效工作承担的准备成本会更高。

归约、哈希、守卫、噪声、同步、证明、换任务与热限制仍需成本。5.20 不是可兑现收益，
也不是物理严格上界：不同算法可能改变每单位协议工作所需的物理运算，CPU/ANE
贡献也不能靠广告 TOPS 相加。15 TH/s 在当前 GPU 计算模型下需要约 30 TFLOP/s，
没有本机实测证据支持通过普通参数调整达到。

## 五分钟算术参考

| 路径 | GPU 时间 TFLOP/s | 墙钟 TFLOP/s | 测量秒数 |
| --- | ---: | ---: | ---: |
| half | 9.663 | 9.297 | 300.0 |
| float | 9.503 | 9.146 | 300.0 |
| mpp | 8.980 | 8.512 | 300.0 |

8×8 的 half/float 路径使用运行时输入、独立累加链和完整输出校验；MPP 为
64×64×128。每个窗口另有 20 秒预热。GPU 时间来自完成的 command buffer；
墙钟还包含编码、等待和周期校验，末次完整校验在测量结束后执行。

这组最高算术参考为 9.663 TFLOPS，当前长测矿工主扫描算术量约
8.469 TFLOPS，二者之比约 87.7%。**这是不同工作负载的
参考比值，不是硬件所有单元利用率，也不是剩余空间一定可以兑现。**
分子使用矿工墙钟吞吐，分母使用合成基准 GPU 时间；最高模式也未必对应生产模式。
MPP 基准反复使用相同输入并保留累加器；实际矿工更换 prefix、清零、store、同步和
折叠。不能把微基准直接转换成可提交的 PRL 算力。

还运行了每轮读取不同 A/B 的控制，避免恒定乘积被移出循环这一机会；它包含更多
内存成本，不能拿较低结果作为纯计算极限。运行时输出校验不是 GPU ISA 审计，
这里不宣称穷尽所有编译器变换或找到不可突破的硬件峰值。

## 为什么分块有效，为什么展开哈希没用

新 kernel 把一次 64×64 输出拆成两个 32×64 子块，共享矩阵由 16 KiB 减为 8 KiB，
减少单个矩阵操作的逻辑累加器规模。所有 128 个线程仍参加矩阵操作和屏障，
使用公开的 tensor store 布局；没有硬编码私有寄存器映射。每个 threadgroup 的
算术量保持 `2×64×64×128 = 4×32×64×128 = 1048576 MAC`。
改善占用率／寄存器压力是与结果相符的解释，但本轮没有硬件计数器证明具体归因。

进一步拆成 16×64，三项 GPU 正确性检查仍通过，但完整扫描只有 **4.0981 TH/s**，
低于前后 32 行控制的均值 4.2345 TH/s，约 -3.22%，因此未采用。
这表明分块并非越小越快；16 行虽然输出缓冲更小，却增加矩阵调用／同步次数。

公开 pipeline 元数据也已读取：旧版静态线程组内存
16384 字节，新版
8192 字节；允许的每组最大线程数
576 →
768。这些是编译后的资源元数据，
不是实测活跃占用率或寄存器数量；实际 dispatch 仍是 128 线程。

阶段消融中，原版 GEMM＋归约约 68.339 ms，
哈希＋目标检查约 0.203 ms，后者约占合并 GPU 阶段
**0.296%**。这解释了为何 MI300X 论文里的大额哈希开销不能套到本机。
GEMM＋归约包含访存和同步，尚不能由该数字单独证明纯 ALU 瓶颈。

| 新网格对照 | 本地 PRL TH/s |
| --- | ---: |
| control-a | 3.9274 |
| unroll-b | 3.8897 |
| control-a2 | 3.9271 |
| rotate-c | 3.8909 |
| control-a3 | 3.9273 |

哈希静态展开使哈希组件更快，但完整扫描约慢 1%；Metal rotate 版本亦没有总收益，
都未部署。此前 private transcript、region 大小和寄存器折叠实验见
[较早的优化报告](OPTIMIZATION_20261030.md)。

## CPU 与其他可用方向

公开 Accelerate `cblas_sgemm` 在 GPU 挖矿同时约为
1.062 TFLOPS；旧 GPU 路径仍为
3.9291 TH/s，前后控制约 3.9272 TH/s，没有观察到明显 GPU 速度损失。
CPU 小整数输入完整 int64 对拍通过。**这没有验证实际 AMX 指令归属，CPU 测试也不是
PRL 矿工，不能把该 FLOP/s 加到矿池算力。** 它支持下一步研究完整 CPU PRL 路径；
还需任务分配、零重复工作、prefix/transcript、证明、费用与真实份额验证。
该 CPU 负载运行约 85 秒，GPU 测量窗口为 60 秒；软件 sys_power 从控制组均值约
63.57 W 增至
74.16 W。这里没有证明长期并行收益或插座能效。

- 已有：混合精度 GEMM、实际输入精度守卫、噪声／固定 B 缓存、紧凑准备、CPU 下一网格
  预备、32 位 BLAKE3、高位优先目标比较、每份 proof 的官方验证。
- 值得继续：按设备的合法分块调参、访问局部性、精确 CPU 后端、实际 GPU 计数器定位。
- 仍未完成：固定三缓冲／persistent kernel、完整异构 PRL 矿工、真正 ANE 执行与挖矿证明、
  M2–M5 真机资格、Metal 硬件 CI。不能为了减少等待取消任务过期或精度检查。
- M5 每个 GPU 核的 Neural Accelerator 与独立 ANE 是不同部件；
  [Apple 已介绍该能力](https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/)，
  本项目尚未实测 M5 性能。

## 原建议里必须修正的假设

1. 64 GB 不推出 32 核 GPU；[官方规格](https://support.apple.com/en-us/111901)列有
   24／32 核选项，本机核心数来自实读。
2. half 不能精确表示所有 4096 以内整数，`63²=3969` 就是反例。half 输入后 float
   乘加与先舍入 half 乘积不同。通用加噪输入保守取 ±127，则完整 K 的和界
   `4096×127²=66064384` 超过 2²⁴；当前路径由已验证的混合精度执行、实际输入 half
   往返检查及 L1 守卫共同限定支持的精确范围，不靠原始输入范围猜测。
3. 没有证明“所有 M1–M4 矩阵／哈希都共用同一批单元”“NVIDIA 哈希免费”或固定
   FP16=FP32 吞吐。按本机路径测量，不从 API 类型列表推断全部物理结构。
4. [PIP-3](https://pearl-research-labs.github.io/pips/pip-0003/)检查时为 Draft、部署 TBD，
   [cert-v4 PR #311](https://github.com/pearl-research-labs/pearl/pull/311)仍开放；没有核实激活高度。
   FP8 解码为 half 不足以复制 H100/B200 累加分组、截断、提升和正负零语义。
   当前 INT 路径与未来 FP8 后端必须分开验证。

## 功耗、温度与证据

新分块 300 秒窗口的软件 sys_power 平均约 64.23 W，
GPU 平均温度传感器最高约 90.93°C。
这是 macmon 软件观测，**不是插座读数**。本轮没有把 powermetrics 当成已取得的数据；
当前 SSH 用户没有其免密 sudo 权限。未据此报告精确整机每瓦效率、电费后利润或收入。

每批只有一个 GPU 研究任务，独立进程组有期限、温度和 thermal pressure 保护。
每批结束核实原生产守护恢复，部署保留同一 worker。首次微基准计划把 MPP 的 chains
错误设为 4，被参数检查拒绝并恢复生产；修为 1 后重新完成，失败收据也保留。

完整数字与文件哈希见 [结构化实验收据](data/m1-ceiling-20261030.json)。
可复现工具和精确性说明在 [research/2026-10-30/ceiling](../research/2026-10-30/ceiling/README.md)。
